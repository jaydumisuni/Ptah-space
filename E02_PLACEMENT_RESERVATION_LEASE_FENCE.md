## Delivered E02 boundary

E02 implements centralized placement authority with distributed evidence inputs and decentralized execution.

The implementation provides:

- deterministic placement against current E01/A02 Node session, capability and resource evidence;
- bounded resource Reservations tied to one exact A04 Attempt and one exact Node generation/connection epoch;
- time-bounded Lease authority with monotonically increasing Fence tokens;
- stale Fence, Generation, ConnectionEpoch, Attempt, Reservation and Lease rejection;
- advisory Node offers that never become execution authority;
- `ptah-control` as the sole issuer of Reservation, Lease and Fence authority;
- dispatch authority carried over the existing `ptah.node.link.v1` E01 envelope;
- Node-side validation before any Provider invocation;
- real `native-process` A05 Provider integration while retaining independent Provider-generation fencing;
- A03-backed append-only Reservation/Lease/Fence recovery without adding an E02 database schema;
- truthful canonical journal timestamps derived from the actual Reservation creation or Lease issue event;
- restart recovery that preserves Reservation accounting and Fence monotonicity while failing closed on malformed or ambiguous durable state;
- D08 remote-placement composition that satisfies only the existing Programme E placement-authority blocker when a real current compatible Node exists.

## Authority progression

The implemented authority progression is:

`requirements -> candidates -> score/offer -> placement -> Reservation -> Lease + Fence -> Dispatch`

No earlier stage implies a later authority. Capability, availability, offer and placement metadata alone cannot dispatch work.

## Existing authorities retained

E02 composes rather than replaces the existing owners:

- A02 remains authoritative for Node identity, generation, capability and resource truth;
- A03 remains authoritative for durable canonical storage;
- A04 remains authoritative for Activity, Operation and Attempt identity;
- A05 remains authoritative for Provider identity, generation and execution;
- E01 remains authoritative for authenticated current Node sessions and stale-session fencing;
- D08 remains authoritative for application/platform compatibility and session semantics.

## Explicit non-claims

E02 does **not** implement or authorize:

- E03 Node-to-Node Object transfer or overlay data plane;
- E04 Workspace movement or collaboration transport;
- E05 platform-specific Node admission policy;
- E06 automatic discovery, relay selection or intermittent/local-first reconciliation;
- a new transport;
- a synthetic Windows/macOS/iOS Node or Application Session;
- a second Provider identity/generation system;
- a new frozen Core entity family or migration.

## Dependency delta

E02 adds no new registry or Git dependency family. It adds the `ptah-placement-runtime` workspace crate and the exact path-dependency edges required to compose it with `ptah-control`, `ptah-node` and `ptah-application-runtime`.

The committed `Cargo.lock` is regenerated by Cargo 1.97.1 for the resulting workspace graph. Existing repository dependency, licence, advisory and source policy remains authoritative.

## Merge rule

A pull request may be merged only when:

1. `main` still equals `18c1bb26bf074fd8146c2dd8e47838d658af8561`;
2. the PR head equals the exact E02 SHA proven by the permanent release workflow;
3. the reviewed changed-path set is unchanged;
4. the guarded merge uses that proven expected head SHA;
5. post-merge verification confirms the merge parents and that the merged E02 side tree equals the proven candidate tree.

The merge itself is not proof. E02 is complete only after the merged tree is independently verified against the proven candidate.
